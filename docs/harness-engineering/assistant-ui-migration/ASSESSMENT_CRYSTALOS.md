## Verdict up front

**`PARTIAL`** — precisely: **do not migrate the runtime; do the contract work; then let Nadia and Theo decide about the rendering layer.**

The reason is narrow and evidential. Every "free" feature that motivates taking the dependency — edit, regenerate, branch, thumbs up/down, thread history — is blocked by a **missing server-side identity**, not by a missing client library. Nothing in `assistant-ui` mints a `turn_id` for us. Adopting it does not unblock those features; it just relocates where we notice they're blocked.

Roughly **9 engineer-days of contract work unblocks all of them for either chassis**, and fixes two shipped-but-inert features and one broken quality metric on the way. Full verdict block in §7.

## 1. The message-identity costing (the crux)

### 1.1 What is actually missing

There is no turn, message, or run identifier anywhere in the Crystal chat path. Not dropped in transit — never minted.

| Layer | Evidence |
|---|---|
| CrystalOS emitter | `crystalos/main.py:1791-1807` — `event_stream()` yields `data: {json}\n\n`. No `id:` line, no `event:` line, no id inside the payload |
| Answer frame | `crystalos/agents/crystal.py:1968-1974` (skill path), `:1983-1989` (fallback), `main.py:1804` (stream-throw fallback) — four keys: `answer`, `citations`, `insight_refs`, `suggestions` |
| Express proxy | `backend/src/routes/experience.ts:820-823` — byte-copies chunks. Nothing to add an id to, and it adds none |
| Frontend | `app/src/components/CrystalPanel.tsx:453,471,537,550,566` — five `crypto.randomUUID()` sites. Every message id is client-minted and dies on reload |
| Telemetry | `crystal.py:1645` — `thread_id=None`, commented "nullable after migration 009" |

### 1.2 The identity we already generate and then throw away

This is the part that makes the costing cheap, and it is worse than `CURRENT_STATE.md` finding #6 describes.

`crystal_turn_events.id` is a `UUID PRIMARY KEY DEFAULT gen_random_uuid()` (`supabase/migrations/20260623000002_crystal_telemetry.sql:6`). It is generated by Postgres inside `_write_turn_event` (`crystalos/lib/turn_publisher.py:75-105`), which is scheduled as a **fire-and-forget task** (`turn_publisher.py:112`, called from `crystal.py:1659`) **after the `answer` frame is already on the wire**. Nobody awaits it. Nobody reads the id back.

Consequences, all traceable to that single fact:

- **`POST /api/crystal/feedback` is uncallable by construction.** `crystalos/routers/feedback.py:21` requires `turn_event_id: str`, FK'd to `crystal_turn_events(id)` (`20260623000002_crystal_telemetry.sql:34`). The endpoint is complete, has a quality-regression detector (`feedback.py:91-92`) and a test suite (`crystalos/tests/test_feedback_api.py`), and has **zero callers** in `app/` or `backend/` (grep confirms). A shipped AI-quality input is inert because the id it needs is minted after the response and never returned.
- **`crystal_debug_traces.turn_event_id`** (`20260623000002_crystal_telemetry.sql:81`) is unjoinable for the same reason.
- **`crystal_turn_events.thread_id` was made nullable to accommodate the defect rather than fix it.** `20260623000009_crystal_turn_events_skill_name.sql:14-15`, comment: *"GAP 7: Make thread_id nullable (fire_telemetry calls before thread is created)."* We migrated the schema to match the bug.
- **The proposal outcome funnel is keyed on a title slug** rather than an id — see §5(a). This is the same root cause wearing a different hat.

So: the identity is not a new concept we need to invent. It is a value we generate one step too late, in the wrong place, and discard.

### 1.3 The fix, layer by layer

**CrystalOS** — mint `turn_id = uuid4()` at the top of `crystal_stream_endpoint` (`main.py:1737`, before `stream_fn()` is chosen at `:1785`). Carry it on `CrystalInput` or a sibling `TurnContext`; `crystalos/lib/trace_context.py` already exists for exactly this shape of per-request async context (it carries `run_id`/`org_id` today), so there is a precedent and no new mechanism.

Do **not** edit every yield site. There are ~11 yields in `_run_skill_stream` alone (`crystal.py:1808, 1812, 1894, 1931, 1941, 1947, 1952, 1962, 1968, 1983, 1992`), ~10 more in `_run_react_loop_streaming`, and 3 in `main.py`'s fallback (`:1802, 1804, 1806`). Wrap the generator once in `event_stream()` (`main.py:1791-1807`): parse each yielded JSON, inject `turn_id`, re-serialize, and emit a real SSE `id:` line alongside `data:`. One helper, one call site. That also gives any `EventSource`-shaped client `Last-Event-ID` for free, which is the standards-compliant version of what `assistant-ui`'s resumable-streams feature does (`ASSISTANT_UI.md:150`).

Emit a leading `{"type":"turn_start","turn_id":…,"thread_id":…}` frame. Pass the pre-minted id explicitly into the `crystal_turn_events` INSERT (`turn_publisher.py:79-105`) instead of relying on `DEFAULT gen_random_uuid()`.

**Express** — the proxy needs no parsing (it byte-copies). It should mint/forward a `message_id` for the *user* turn and set an `X-Crystal-Turn-Id` response header before `flushHeaders()` (`experience.ts:654`) for non-SSE consumers. It must also stop dropping query params (§5(d)) — same PR.

**Frontend** — adopt the server id at the five `crypto.randomUUID()` sites, keeping the client uuid as a fallback for locally-constructed messages (errors, optimistic user echo). `Message.id` already exists (`CrystalPanel.tsx:602`-adjacent interface).

**Persistence** — one row per turn is already the shape of `crystal_turn_events`; the message log itself belongs in `crystal_threads` v2 (§4), which shares this plumbing.

| Work | Days |
|---|---|
| CrystalOS: mint + inject via one generator wrapper; thread `turn_id` into telemetry; tests (CrystalOS rules require a test per changed signature — `crystalos/CLAUDE.md` "Testing rules") | 1.5 |
| Telemetry: explicit id on INSERT, real `thread_id`, make `feedback.py` reachable | 0.5 |

| **Total** | **≈5.5 days** (≈1.5 weeks with review) |

### 1.5 Is it worth doing on its own merits?

**Yes, unambiguously, and it is the highest-value contract change in this assessment.** It is worth doing if we adopt `assistant-ui`, if we reject it, and if we never discuss it again. Independent of any UI decision it delivers:

1. Thumbs up/down — a built, tested, zero-caller feature (`feedback.py`, `tests/test_feedback_api.py`) becomes callable.
2. A correct proposal funnel key (§5(a)) — i.e. we can state our accept rate for the first time.
3. Joinable per-turn provenance (`crystal_debug_traces`).
4. A non-null `thread_id` in telemetry, retiring the migration that codified the bug.
5. Regenerate and edit, *if* the frontend wants them.

### 1.6 The honest caveat: ids alone do not buy edit/regenerate/branch

Stable identity is necessary, not sufficient. Splitting the three:

- **Regenerate — cheap once ids exist (~1 frontend day).** Conversation history is a request-body field, not server state (`CrystalPanel.tsx:352-354`; `CrystalInput.conversation_history`, `crystal.py:121`). "Regenerate turn N" is literally "resend with history truncated before N." No server change beyond ids.
- **Edit — same plus composer wiring (~1.5 days).**
- **Branching — do not build it.** Not on cost grounds; on correctness grounds. Every turn re-uploads its own grounding corpus from the client (`CURRENT_STATE.md` #4: `CrystalPanel.tsx:344-351`, server-merged "client wins if non-empty" at `experience.ts:720-732`). Two branches of the same question, asked from two different pages, were grounded on **different insight sets** — so a branch picker would present incomparable answers side-by-side as if they were alternatives to the same question. That is a Crystal-specific reason to decline a "free" library feature, and it is a better reason than "it costs too much." If we ever want branching, the prerequisite is server-side grounding (kill finding #4), not a UI library.

**Net for the mandate question:** the marquee features are not free, they are ~5.5 days of *our* contract work followed by ~2.5 days of client work — and the library contributes none of the 5.5.

## 2. Token deltas: **no**

`assistant-ui` does not require them (`ChatModelAdapter.run()` accepts a single complete result — `ASSISTANT_UI.md:58-65`), so this is purely a UX call. My answer is no, and the reason is not "it's a lot of plumbing." It is that **the answer text is not final at generation time**, by design.

### 2.1 Three places already-generated prose is discarded

| # | What discards it | Evidence |
|---|---|---|
| 1 | JSON/Pydantic validation retry — appends a correction message and re-calls | `crystalos/lib/openrouter.py:445-457`, validation at `:490-492` |
| 2 | EVALS gate retry — one full re-synthesis that **replaces** `output_raw` entirely | `crystalos/lib/skill_runtime.py:152-186` (see `:181`) |
| 3 | Eval still failing → the whole skill output is thrown away and a **different** LLM call produces a **different** answer | `crystal.py:1352-1359` returns `None`; `_run_skill_stream` falls through to `_run_crystal` at `:1978-1989` |

Streaming deltas from the first attempt means streaming text the quality gate may reject. The platform's entire "eval-gated skill" premise (`crystalos/CLAUDE.md`, "SkillRuntime quality gate") is that the user never sees an ungated answer. The options are all bad: (a) ship ungated prose and demote the gate to an offline metric — a real product regression on the AI-safety story; (b) stream only the final attempt — which is exactly what happens today; (c) invent a visible "revising…" retraction UX.

### 2.2 The payoff is also small, and pointed at the wrong phase

`crystal-analyst` runs `google/gemini-2.5-flash` with `max_tokens=1200` (`crystalos/lib/models.py:411`) and the skill *instructs* 2-5 sentences (`crystalos/skills/crystal-analyst/SKILL.md:32`, output schema `:65-68`). That is roughly 60-120 output tokens. Streaming buys about a second.

Meanwhile the turn's real latency is:

1. **Up to 3 sequential Postgres tool calls** — `crystal.py:1912-1947` is a `for` loop of `await dispatch_tool`, not a `gather`.
2. **The synthesis LLM call.**
3. **Sequential LLM-judge calls.** `skill_runtime.py:427-470` uses an LLM judge for any criterion not matching `STRUCTURAL_KEYWORDS` (`:53-56`). For `crystal-analyst` (`skills/crystal-analyst/EVALS.md`), E1 is structural ("valid json"), but **E2, E4 and E5 are not** — "present and non-empty", "are specific follow-up questions", "reference actual data" match none of the keywords. So **three sequential judge calls** run between generation and emission. E2 is `must pass`, and the judge's error fallback is `0.5` (`skill_runtime.py:469-470`), so a single judge hiccup fails a must-pass criterion and triggers the retry.
4. Possibly all of 2+3 again.

**We already stream the slow part** (`thinking`/`observation`/`synthesizing`). Token deltas would stream the fast part, and could not even start until the gate cleared — which is the moment we already emit.

### 2.3 What to do instead (cheaper, larger win)

| Fix | Cost | Effect |
|---|---|---|
| `asyncio.gather` the ≤3 prefetch tools (`crystal.py:1912`) | 0.5 d | Real latency cut, no contract change |
| Parallelize the EVALS criteria loop (`skill_runtime.py:376-382`) | 0.5 d | Real latency cut, no contract change |
| Emit a `verifying` SSE frame so the eval wait is legible instead of hidden inside `synthesizing` | 0.5 d | Honest UX — the user learns the answer is being checked |

### 2.4 If we ever *do* stream prose, here is how the structured fields still arrive reliably

The question deserves a concrete answer, not a deferral. **Two-channel output: stream the prose, deliver the structure atomically.**

- **On an Anthropic-SDK model this is native and already half-built.** `crystalos/lib/anthropic_client.py:79-98` defines a single tool whose `input_schema` **is** the Pydantic output schema, and forces it with `tool_choice={"type":"tool","name":…}`. And `:111-117` already consumes a real `client.messages.stream()` — it iterates every event and keeps only `thinking_delta` text (`:114-116`, surfaced as `entry.thinking_text` at `:156`), discarding the rest. A model can return a `text` block *and* the forced `tool_use` block in one response. So: stream text deltas as `answer_delta` frames; emit `citations` / `suggestions` / `insight_refs` / `action_proposals` from the `tool_use` block as the terminal `answer` frame. **The structured half remains one atomic, Pydantic-validated object — zero loss of guarantee.** Note we already stream and discard readable reasoning text; streaming *that* is a better first move than streaming the answer.
- **On the current path it does not work and should not be attempted.** `crystal-analyst` goes through OpenRouter with `response_format: {"type":"json_object"}` (`openrouter.py:214-215`). There is no text/tool split. You would be incrementally parsing a partial JSON object, praying `answer` is the first key, against a pipeline whose first step is `_strip_markdown_fences` (`openrouter.py:385-391`) — which needs the complete string to strip a trailing fence, and also strips `<think>…</think>` blocks that some models emit mid-stream. Fragile in three independent ways.
- **Either way, the eval gate must still run on the structured half before emitting, and streamed prose is therefore ungated.** That is a product decision, not an engineering one.
- **Cost of the Anthropic-path version: ~4 days**, dominated not by the SDK work but by `SkillRuntime.execute()`'s signature: it returns a single `SkillResult` (`skill_runtime.py:68-75`) awaited by 2 production call sites and ~15 tests. Turning it into a generator is the expensive part. Plus routing `crystal-analyst` to an Anthropic model, whose cost/latency implications are outside my mandate.

**Ruling: no token deltas.** Do §2.3 instead. Revisit only if answers get long (they are architecturally short) or if `crystal-analyst` moves to the Anthropic SDK path for unrelated reasons.

## 3. Proposals as tool calls — the highest-leverage question

### 3.1 Ground truth, sharper than the evidence base states

There are two proposal emitters and **only one is reachable from a browser.**

- **Tool path** — `_extract_action_proposals` (`crystal.py:972-984`) reads results of the 15 `propose_*` tools (`crystalos/crystal/registry.py:1009-1016`). It is called from **exactly one place**: `_run_react_loop_streaming` (`crystal.py:1453`), the legacy ReAct loop. That path requires `?legacy=true` (`main.py:1722, 1786`), which the Express proxy **drops** — `experience.ts:789` builds the upstream URL with no query string. It *additionally* requires `user_role in ('admin','brand_admin')` (`main.py:1747`), while the browser bridge never sends `user_role` at all (absent from the client body at `CrystalPanel.tsx:344-378`, never set in `agentBody` at `experience.ts:706, 733-756`), so `main.py:1744` defaults it to `"viewer"`. **Doubly unreachable.**
- **Skill path** — an optional `action_proposals[]` array inside the one JSON object (`skills/crystal-analyst/SKILL.md:70-81`), normalized at `crystal.py:1204-1214`, emitted at `crystal.py:1961-1965`. And `crystal-analyst`'s `allowed-tools` line (`SKILL.md:13`) contains **zero action tools** — the skill physically cannot call one.

So today **100% of browser-visible action proposals originate as an optional array field in a single JSON object produced by one LLM call, gated by an eval that can discard the entire thing.** The honest framing is therefore not "out-of-band vs. tool call." It is: **CrystalOS already built model-chosen action tool calls and deliberately retired them** in favour of deterministic prefetch + one eval-gated synthesis (`crystalos/CLAUDE.md`, "Crystal Intelligence (skill-first streaming — default)"). "Proposals as tool calls" is a proposal to partially un-retire that architecture.

### 3.2 Should CrystalOS emit real model-chosen tool calls? **No.** Should proposals become identified first-class objects? **Yes.**

**What breaks if we go to real model-chosen tool calls:**

1. **Model-chosen means model-gated.** Today proposal *content* is eval-gated by E1-E5 alongside the answer (`skill_runtime.py:152`, `crystal.py:1352`). A mid-turn tool call is emitted **before** synthesis and **before** the eval, so we would be shipping an unvetted write-proposal into the confirm-card. The confirm-card's entire purpose is the safety boundary — "Crystal proposes, the app executes" (root `CLAUDE.md`; `requires_confirmation: bool = True  # always True — safety guarantee`, `crystal.py:173`). Regressing its quality gate to buy a cleaner client abstraction is the wrong trade, and it is the one trade I will not sign off on.
2. **Latency and cost regress.** It means restoring an LLM tool-selection turn (`_react_plan_tools`, `crystal.py:1002+`, looping to `CRYSTAL_MAX_TOOL_TURNS`) — exactly the cost the skill-first migration removed.
3. **`crystalos/novu_connect/message_processor.py:130-174` breaks.** It calls `crystal_agent.run(inp)` in-process (`:162`) and returns `output.answer` as a bare string for Slack/Teams/WhatsApp/email (`:163-167`). `CrystalAgent.run` returns `(CrystalOutput, [])` (`crystal.py:1999-2009`). There is no SSE loop, no message parts, no confirm-card surface, and **no user who can click**. A `requires-action` tool call awaiting a human result either blocks forever or needs an auto-decline policy. (Side note: this is also the *only* caller anywhere that populates `user_role` — `:158-159`.) Any tool-call design must therefore preserve a **non-interactive mode** where proposals are collected, not awaited. Cheap to honour up front; expensive to retrofit.
4. Also in scope: `_normalize_proposal`/`_extract_action_proposals` become the wrong shape; `crystal_action_proposals` needs `turn_id` + a real CHECK; and the frontend's 18-branch switch (`CrystalPanel.tsx:754-1021`) becomes 20+ registered tool renderers — Nadia's LOC problem, but note it is a **rewrite**, not an adaptation.

### 3.3 My counter-proposal: server-minted proposal objects

Keep the emission point exactly where it is — after synthesis, inside the eval gate. Change only the *contract*. In `_normalize_proposal` (`crystal.py:952-969`), give every proposal:

- `proposal_id` = `uuid4()` — **not** the current title-derived slug (`crystal.py:964-966`);
- `turn_id` from §1;
- a `type` validated against a shared enum (§5(b));
- an `emitted` row written server-side *before* the frame goes out (§5(a)).

**Cost: ~2 days CrystalOS + ~1 day backend + tests.** It fixes three separate defects, keeps the eval gate, keeps Novu working, adds no LLM turn — and produces exactly the `{id, args, status}` triple that `ToolCallMessagePartComponent` consumes (`ASSISTANT_UI.md:116-128`). **A client-side adapter can then synthesize a tool-call message part from that object with no further server change.** The library gets the shape it wants; we don't buy model-chosen tool calling to get it.

**One contract change I *will* champion, for Nadia:** fold `action_proposals` into the terminal `answer` frame and deprecate the separate event. Today proposals can precede the answer (`crystal.py:1961-1965` before `:1968`; in the legacy path by several seconds, `:1454-1455` before `:1467`). One turn should be one message with parts — ordered, eval-gated, identified. That is ~0.5 day in `crystal.py`, strictly better framing regardless of chassis, and it removes the main structural reason a message-part model would fight our stream.

## 4. Thread persistence — resolution

### 4.1 There are **four** implementations, not three

`CURRENT_STATE.md` §4 undercounts by one.

| # | Implementation | Status |
|---|---|---|
| 1 | `crystal_threads` v1 — `thread_key UNIQUE` (`supabase/migrations/20240518000000_insights_v2.sql:42-55`) | **Statically dead.** Written only at `backend/src/routes/insights.ts:1463-1475`, reached only by `api.crystalChat` → `POST /api/insights/:surveyId/crystal` (`app/src/lib/api.ts:2184-2201`), called only in the `else` branch of `if (CRYSTAL_STREAMING)` at `CrystalPanel.tsx:602` — where `CRYSTAL_STREAMING` is a hardcoded `true` (`:29`) |
| 2 | `crystal_threads` v2 — `(org_id, user_id, survey_id, scope)` (`20240521000002_crystal_threads_v2.sql:3-18`) + `context_state` (`20260603000003:7-20`); writers `get_or_create_thread`/`append_to_thread` (`crystal.py:219-307`) | **Dead.** Zero production callers (grep: definitions + tests only) |
| 3 | `MemoryManager` L2 thread compression (`crystalos/lib/memory.py`) | **Half dead.** `get_memory_manager` *is* called in production — but only for L3 survey-facts warming (`crystal.py:1441-1444`, legacy path; `graphs/insights.py:5178`). The L2 half is unreachable, and `_skill_synthesis` hardcodes `context_state.decisions: []` and `org_memory_facts: []` (`crystal.py:1332-1340`) — **the skill is told there is no memory on every single turn** |
| 4 | React `useState` (`CrystalPanel.tsx:196`) | The live reality |

And the SSE path — the only live path — writes to **no** thread table at all. `api.crystalChat2` → `POST /api/experience/crystal` (`api.ts:2205-2218`) is the SSE-failure fallback and persists nothing either.

### 4.2 Recommendation: keep exactly one — **`crystal_threads` v2**, keyed `(org_id, user_id, survey_id, scope)`

Three reasons, in order of weight:

1. **v1's identity key is a privacy defect, not just a design mismatch.** `thread_key = crystal:${req.orgId}:${surveyId}` (`insights.ts:1493, 1512`) has no user component — **every user in an org shares one conversation thread.** That is disqualifying on its own.
2. v2 already has the columns the feature needs: `last_active_at`, `message_count`, `turn_count`, `storage_expires_at`, `context_state`.
3. Its writer functions already exist and are tested; they just aren't called.

**Concretely:**

- Call `get_or_create_thread` at the top of `_run_skill_stream` (`crystal.py:1804`); emit `thread_id` on the `turn_start` frame (§1); `append_to_thread` for the user and assistant turns; pass the real `thread_id` into `TurnEvent` — killing `crystal.py:1645`.
- Repoint `GET`/`DELETE /:surveyId/crystal/history` (`insights.ts:1492-1517`) off `thread_key` onto the v2 key + `req.userId`. **Keep the endpoints** — they are correct code over the wrong table shape. Then wire the two existing zero-caller client methods (`api.getCrystalHistory`/`clearCrystalHistory`, `api.ts:2231-2245`).
- Retire v1: delete the unary write (`insights.ts:1463-1475`), leave `thread_key` nullable for one release, then drop it.
- **Add the sweep `storage_expires_at` has been promising since 2024** (`20240521000002:6`). `crystalos/scheduler.py` already has `run_retention_job` and `run_scheduler_once` with an env-gate convention — this is ~20 lines in an existing nightly job.
- Either wire `MemoryManager` L2 or delete it. Do not leave a third implementation warm.
- **Do not build branching** (§1.6).

### 4.3 Before, during, or independent?

**Before, and independent of, any migration.** Not because a migration needs it — because:

1. It is the #3 user-visible gap in `CURRENT_STATE.md` §6 and it is ~3 days.
2. It removes 2 of 4 dead implementations, so a migration (or a hand-built fix) inherits **one** thing instead of four.
3. It shares the `turn_id`/`thread_id` plumbing with §1, so doing them in one pass is materially cheaper than either alone.

If we later adopt `assistant-ui`, `RemoteThreadListAdapter` (`ASSISTANT_UI.md:149`) can front this table and we skip the Assistant Cloud upsell entirely. That is a *consequence* of doing the work, not a justification for it.

## 5. Fix-or-file

| | Defect | Severity | Migration-blocking? | Fix regardless? | Cost |
|---|---|---|---|---|---|
| a | Proposal funnel: `emitted` never written **and** the upsert key is a title slug | **HIGH** | No | **Yes — first** | 1.5 d |
| b | `ActionProposalType` exists only in TypeScript; 3 members already drifted | MEDIUM | No | **Yes** | 1 d |
| c | `answer.documents[]` consumed with no server emitter | MEDIUM | No | Decide: emit or delete | 0.5 d |
| d | Proxy drops query params — and `user_role` never reaches CrystalOS | **MEDIUM** (the `user_role` half) | No | **Yes** | 0.5 d |
| e | Eight mismatched/orphaned admin + support endpoints | LOW each, HIGH aggregate | No | **Yes** | 1 d |
| f | `POST /api/crystal/feedback` uncallable by construction *(new — not in the evidence base)* | MEDIUM | No | Free with §1 | 0 d |

### (a) The proposal funnel — HIGH, fix first

Worse than reported. The upsert key is `(org_id, proposal_key)` (`insights.ts:2317`; unique index `20260623000010_crystal_action_proposals.sql:29-31`), and `proposal_key = proposal.id` (`CrystalPanel.tsx:762, 1096`). For skill-path proposals — i.e. **all** browser-visible ones (§3.1) — `proposal.id` is a **title-derived slug**, because `_normalize_proposal` synthesizes it from the title (`crystal.py:964-966`) and the skill output schema has no `id` field at all (`skills/crystal-analyst/SKILL.md:64-77`).

Therefore the same recommendation offered to the same org next week **collapses onto the same row and overwrites its status.** The funnel is not merely missing its top — its denominators are structurally wrong, and a later `dismissed` can silently overwrite an earlier `succeeded`. There is also no `CHECK` on `status`; the five legal values are documented in a **comment only** (`20260623000010:17, 36`).

Fix: server-side `emitted` write at emission time, `uuid4` `proposal_id`, a `turn_id` column, and a real `CHECK (status IN (…))`. This is the **measurement of the closed loop** the root `CLAUDE.md` calls "the unlock." Right now we cannot state our accept rate. Fix it first, after §1.

### (b) `ActionProposalType` source-of-truth drift — MEDIUM

`app/src/types/index.ts:782-807` (25 members) is the only enumeration; CrystalOS validates a free `str` (`crystal.py:165`). Drift confirmed: `workflow`, `template`, `export_insights` are declared in TS with no dispatcher case → they fall to `default` (`CrystalPanel.tsx:1009-1011`).

The asymmetry matters: `_PROPOSAL_TYPE_ALIASES` maps `workflow → create_workflow` (`crystal.py:934`), so a *tool*-emitted `"workflow"` is fine — but a *skill*-emitted `type: "workflow"` passes through `_normalize_proposal` **unaliased**, because `type` is already set (`:962-963`), and lands on `default`. And `ActionProposal`'s own field comment (`crystal.py:165`) **advertises `workflow` and `template`** as valid types. Our Pydantic model documents three types the frontend cannot execute.

Fix: make CrystalOS the source of truth (`Literal[...]` / `StrEnum` on `ActionProposal.type`), mirror or generate the TS union, add a parity test, and correct `crystal.py:165`'s comment. A migration makes this **worse** if unfixed: a tool-renderer registry keyed by tool name also fails silently on an unregistered name.

### (c) `answer.documents[]` has no emitter — MEDIUM

Confirmed from the server side: the `answer` frame is constructed at `crystal.py:1968-1974`, `:1983-1989` and `main.py:1804` with exactly four keys, none of them `documents`. `render_hint:'document'` appears only inside tool-result dicts (`crystalos/crystal/tools.py`). The client half is merged and live (`CrystalPanel.tsx:416, 449, 459` → `InsightDocumentCard`).

This is not a bug; it is an unshipped feature with the client half already in `main`. **My preference: emit it.** CrystalOS already knows which tool results carry `render_hint='document'` (`get_insight_report`, `get_tag_report` — `crystalos/CLAUDE.md`), so forwarding them onto the answer frame is ~0.5 day, and an in-message report card is genuinely differentiated. Alternative is deleting the dead client branch. Either way, **decide** — don't leave it. Joint owner with Nadia.

### (d) Dropped query params — and the `user_role` pin — MEDIUM

Broader than reported. `crystal_stream_endpoint` takes **three** query params (`debug`, `store_trace`, `legacy` — `main.py:1720-1722`), and the proxy's `fetch` (`experience.ts:789`) appends **no** query string, so all three are unreachable: debug events, trace storage, and the entire legacy ReAct path.

The serious half is `user_role`. Even with params forwarded, `main.py:1747` would refuse, because `user_role` never reaches CrystalOS — absent from the client body (`CrystalPanel.tsx:344-378`) and never set in `agentBody` (`experience.ts:706, 733-756`), so `main.py:1744` yields `"viewer"`. But `user_role` is not only a debug gate: `BrandContext`/`ROLE_PERMISSIONS`/`_resolve_permissions` (`crystalos/crystal/context.py`) gate **which tools Crystal may use per request** (`crystalos/CLAUDE.md`, "BrandContext / permissions"). **The chat path is permanently pinned to the least-privileged role.** An org admin in the browser gets a viewer's tool set. The only caller anywhere that sets it is Novu (`message_processor.py:158-159`).

Fix (0.5 day): derive `user_role` **server-side** in `experience.ts` from the Clerk claims / RBAC the backend already has — explicitly **not** from the client body, which `main.py:1744` would currently trust. Forward `debug`/`legacy` in the same PR (one line). Note `main.py:1744-1746` already whitelists the value, which is the right defence but is defending against the wrong source.

### 6.2 With Theo — are the a11y and i18n gaps frontend-only or contract-shaped?

**Mostly frontend, with two real contract dependencies. On both, the bug is mine, not his.**

## 7. Verdict

**`PARTIAL`** — `DON'T` migrate the runtime; **`DO`** the contract work; then let Nadia and Theo rule on the rendering layer.

**Confidence: high (~0.8)** on the contract half. **Medium** on the library half, which is not my call to make.

### The direct argument

Every feature that motivates the dependency — edit, regenerate, branch, feedback, history — is blocked by missing **server-side identity**, not by a missing client library (§1). Nothing in `assistant-ui` mints a `turn_id` for us. We would pay a pre-1.0 dependency plus a ~1,450-LOC rewrite of the differentiated surface, against `unstable_`-prefixed APIs (`ASSISTANT_UI.md:61, 67`), and those features would **remain blocked afterwards**. Conversely ~9 engineer-days (§1's 5.5 + §4's 3, sharing plumbing) unblocks all of them for *either* chassis, and fixes two shipped-but-inert features and one broken quality metric on the way.

### Strongest argument against my own verdict

I am judging a UI library by whether it fixes contract defects — which is not what a UI library is for — and that framing lets me arrive at "fix the contract" without ever weighing the thing I am least qualified on: that Crystal's chat surface is a 2,799-line single file with **one** aria attribute, 12 `t()` calls, and no markdown rendering. That is the state a team reaches when it hand-builds a chat chassis for two years.

My plan makes the contract excellent and leaves the surface hand-built by the same team under the same incentives — and adds ~9 days of work that produce **zero user-visible change** before anyone renders anything differently. A less charitable reading is: *the contract engineer recommends contract work.* If the real failure mode here is organizational — that generic chat affordances never ship because they are never anyone's feature — then adopting a library that makes them free-by-default is the right answer **even if my technical analysis is entirely correct**, and my sequencing is how the UI work slips another two quarters.

### What would change my mind

**→ `MIGRATE`:**

1. Nadia demonstrates the `ExternalStoreRuntime` adapter over Crystal's existing `messages` array (`CrystalPanel.tsx:196`) in **under 300 LOC** with the citation layer and confirm-cards intact — i.e. the differentiated 40% survives as custom parts instead of being rewritten. That is `README.md` test #3, and it is empirical rather than arguable.
2. Evidence that users are actually blocked today by markdown / a11y / persistence. This pod has no user research and no PM (`TEAM.md:96`). If the gap list is user-confirmed and urgent, "9 days of invisible contract work first" is the wrong *sequence* even if it is the right *work*.
3. `assistant-ui` reaching 1.0 with `unstable_assistantMessageId` / `unstable_threadId` promoted to stable. Today the exact API that would consume my new `turn_id` sits on the surface their own policy says may change in a patch release. That is not a reason to skip the contract work — it *is* a reason not to shape the contract around their field names.

**→ `DON'T`, flat:** Theo finds the brand-token cascade requires forking styled components **and** Nadia's adapter lands over ~800 LOC. Then it is two chat surfaces (`XperiqCopilot` included) on a fork of a 0.x library, and the answer is no.

### Mandate answer — does this migration make the closed loop stronger or weaker?

**As currently scoped: weaker, marginally — and not for the reason people expect.** Not because the library cannot render confirm-cards; it can, and its tool-UI shape (`ASSISTANT_UI.md:116-133`) is a better fit than what we have.

Weaker because the loop's four steps are **unequally healthy, and a migration touches only the healthy ones**:

| Step | Health |
|---|---|
| **propose** | Healthy but mis-shaped — an optional array field in a JSON blob (`crystal.py:1961-1965`) |
| **confirm** | Healthy — 18-branch switch, 12 endpoints, works, well tested |
| **execute** | Healthy — with DataBus invalidation |
| **record outcome** | **Broken** |

*Record outcome* is the step that closes the loop back into skill quality, and it is broken in five places at once: `emitted` is never written; the upsert key is a title slug so repeat emissions overwrite each other (§5(a)); `GET .../crystal/proposals` has no caller (`insights.ts:2348`); `crystal_feedback` is uncallable (§5(f)); `crystal_turn_events.thread_id` is null by design (`crystal.py:1645`). **Every outcome we do record is unjoinable to the turn that produced it** — which means outcomes cannot feed back into skill examples or evals. The root `CLAUDE.md`'s claim that "each turn also emits telemetry the next tier learns from" is, for the chat path, currently **false**.

A migration rewrites *confirm* and *render*, leaves *record* exactly as broken, and consumes the quarter in which we would otherwise have fixed it. That is how it makes the loop weaker: **opportunity cost on the only broken step.**

The version that makes the loop **stronger** is §1 + §5(a) + §4: mint `turn_id` and `proposal_id` server-side, write `emitted` at emission, put `turn_id` on the proposal row, make `crystal_feedback` callable, persist the thread. That closes the loop for the first time — and *afterwards* `assistant-ui` becomes both a reasonable rendering choice and a materially cheaper one, because the ids its `unstable_` APIs want will already exist.
