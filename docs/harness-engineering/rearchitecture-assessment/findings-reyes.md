## 2. Simplification opportunities

1. **`EXAMPLES.md` is a dead/misleading artifact for ~2/3 of skills and should either be wired in or retired — not left as-is.** `SkillRuntime._build_system()` (`lib/skill_runtime.py:276-306`) assembles the system prompt from exactly three sources: the `SKILL.md` body (`_body`), files under `references/*.md`, and up to 3 rows from the **Postgres `skill_examples` table** via `_fetch_examples()`. Nothing in the codebase ever opens `skill_meta["examples"]` (`grep '\.get("examples")'` across the repo returns zero hits outside test assertions on the frontmatter field itself) — the path is parsed into metadata and never dereferenced. Meanwhile, on disk: 24 of the ~46 `skills/*/EXAMPLES.md` files are the 2-line auto-generated placeholder (`<!-- Auto-generated from skill_examples DB table. Do not edit manually. -->`, currently empty because nothing has ever written to it — no script anywhere in the repo generates this file from the DB table either, so even the placeholder's own comment is inaccurate), but **8 skills have genuinely hand-authored example content** (`workflow-analyst/EXAMPLES.md` — 468 lines; `crystal-support` — 202; `metric-parity` — 84; `taxonomy-mapper` — 74; `schema-mapper` — 70; `platform-gap-tracker` — 52; `executive-briefing` and `xm-market-researcher` — 40 each). Someone spent real authoring effort writing detailed worked input/output examples for those 8 skills, and **none of it ever reaches the model or the router.** This is pure wasted effort today, and it's exactly the kind of thing a harness-hygiene pass (à la Claude Code's `/doctor`, cited approvingly in doc `01`) would catch. Two honest fixes, either is fine: (a) have `_build_system()` fall back to parsing `EXAMPLES.md`'s worked examples when the DB bank is empty (turns 8 skills' existing investment into real day-one few-shot quality, and gives every new skill a bootstrap path before it has production traffic to draw on — arguably better than the current design, where a brand-new skill gets zero examples until it accumulates its own history), or (b) delete the unused frontmatter convention and file convention entirely and document plainly that few-shot examples are DB-sourced only. Leaving it as dead weight that looks load-bearing is the one option that should not survive this assessment.

2. **`csat-action-advisor`, `nps-action-advisor`, and `ces-action-advisor`'s `EVALS.md` files each carry a near-identical criterion** — "includes a quantified impact estimate" (CSAT E4: "business rationale includes a quantified impact estimate," similarly shaped criteria in the NPS/CES siblings) — **currently graded by a full LLM-judge call** (`_eval_criterion` → `get_model("insight_evaluate")`, a live model round-trip per skill invocation, per retry) because the criterion text doesn't match any of `STRUCTURAL_KEYWORDS` (`"count"`, `"contains"`, `"non-empty"`, etc. — `skill_runtime.py:53-60`). "Does this string contain a number followed by `%`/`points`/`pts`/`days`" is a five-line regex, not a judgment call. This is the single cheapest, most concrete instance of the §3.1 deterministic-post-processing pattern available in the current skill corpus, and it generalizes across at least 3 skills sharing the same criterion shape — see the experiment design in §4.

## 3. Improvement opportunities — evidence audit of the synthesis doc's claims

The brief asks me to be skeptical about cited numbers. Going through synthesis §2/§3 pattern by pattern, sorted into three evidence tiers:

### Tier A — engineering hygiene, doesn't need a benchmark to justify (adopt on code-review merit alone)
Provenance stamping (#2), tool-error-contract formalization (#3), routing verbose output to logs (#4), the "when can this be removed" living table (#6). None of these claim to move a quality metric — they're operational hygiene. The right validation is a code review, not an experiment. Low effort, low risk, adopt without ceremony (Priya's lens for exact sizing).

### Tier B — a single cross-validated finding (genuinely strong evidence)
**§3.1's pattern #5 (deterministic post-processing over LLM re-derivation) is the one item in the entire research pass with real independent corroboration, and I confirmed it's not aspirational for CrystalOS**: `agents/crystal.py:1212` (`_build_viz_for_citations`) is real, shipped code with its own docstring citing "Tier-0 deterministic chart selection... never model-chosen," matching the synthesis's description exactly. Three of the four convergent examples (QAH's driver-analysis tool, QAS's `compile_logic.py`, CrystalOS's own `_build_viz_for_citations`) are **engineering teams independently solving a design problem, not vendors selling a harness product** — that's a meaningfully different (stronger) evidence class than most of the rest of this research pass. The fourth data point, the AIP paper's "53%→67%," is a single benchmark number from a different task domain (the doc doesn't specify what AIP's benchmark actually is, only that it's "Claude Sonnet's pass rate" on typed skill-graphs) — **that number should not be quoted as a prediction for CrystalOS's own skills.** The pattern (push provably-correct logic out of the LLM) is well evidenced; the magnitude (53→67 points) is not transferable evidence and citing it as if it predicts a CrystalOS outcome would be a rigor failure.

### Tier C — plausible but single-source, vendor-reported, or mechanism-mismatched (do not adopt on faith; test cheaply first or skip)
- **"73%→85% routing accuracy from negative examples" (OpenAI).** This is the number the brief specifically flagged as suspect, and it should stay flagged: it's a self-reported vendor number with no visible methodology (skill-corpus size, routing mechanism, confidence interval) in the source doc, and — more importantly for CrystalOS specifically — **it's not even clear the mechanism transfers.** OpenAI's routing (per doc `01`'s own framing, and QAS/deepagents' `SkillsMiddleware`) is *in-context*: all candidate skill descriptions sit in the system prompt simultaneously and the model picks one. CrystalOS's `skill_registry.find()` is *retrieval-based*: each skill description is embedded once at `warm_router()` time, and routing is a cosine-similarity search against the query embedding (`lib/skill_registry.py:232-262`) — the model never sees competing descriptions side by side. "Negative examples sharpen contrastive discrimination when an LLM is choosing among several options in front of it" is a different claim from "negative examples reshape an embedding well enough to change nearest-neighbor rank" — these could have very different effect sizes, or even opposite ones (a longer description padded with negative phrasing could pull an embedding *away* from genuinely close queries). **This is exactly the kind of transfer risk the brief asked me to name explicitly, and it also invalidates half of the synthesis's own recommended fix** — see the correction in §2.1 and the experiment in §4b.
- **LangChain's "≤12 skills" ceiling.** CrystalOS already has ~46 skills, roughly 4x past this cited ceiling, with apparently no measured degradation flagged anywhere in `cdx.py`'s admin quality metrics. But the ceiling was measured on Claude Code's *in-context* skill list (same mechanism mismatch as above) — whole-list attention dilution, not embedding retrieval. It is not evidence that CrystalOS's ~46-skill embedding-retrieval router has a problem, nor evidence it doesn't; it's simply not the same measurement. **Open question, not a finding** — see §6.
- **Harness-Bench "5-23pp swings," LangChain's Terminal-Bench rank-30-to-top-5 case study, deepset's ranking-position study, Microsoft's Azure SRE Agent "45%→75% Intent Met," TencentDB's memory numbers, Anthropic's "17% overeager actions," "20%→40% auto-approve trust curve."** Every one of these is a vendor (or the vendor's own tooling team) reporting a result about its own product, in a vendor blog post, with no third-party replication cited anywhere in the four source docs. That doesn't make them false — it makes them **self-reinforcing rather than independently reproduced**, per the brief's ask #5. None should be cited in a CrystalOS design doc as if they predict a CrystalOS outcome; they're motivation for *trying* a pattern, not evidence it *will* work here.

## 4. Can CrystalOS test this itself? (ask #2) — mostly yes, with one concrete gap

CrystalOS already has more experiment infrastructure than the synthesis doc credits it for:

- **`lib/skill_registry.py`'s `SkillVariant`/`resolve_variant()`** — a full skill-level A/B framework (`variant`, `rollout_pct`, `baseline_variant`, `min_sample_size` frontmatter fields, consistent MD5-hash bucketing per user) already exists and is tested (`tests/test_ab_testing.py`).
- **`lib/cdx.py`'s `_check_significance()`** — a two-proportion z-test (α=0.05) already gates variant graduation/rollback on statistical significance against `min_sample_size`, not vibes.
- **`lib/cdx.py`'s `/api/cdx/test` dev endpoint** — returns the top-5 routing candidates (`registry.find_with_scores`) plus full skill execution and per-criterion eval detail in one call — a ready-made routing-debug harness.
- **`skill_quality_metrics` (aggregated nightly) + `crystal_turn_events`** — already track `avg_eval_score`, `neg_rate`, `p50_latency_ms` per skill in production, surfaced via `/api/admin/skills`.

**What's missing is narrow and specific**: none of the above measures *routing accuracy* against ground truth — they measure *output-quality eval score* once a skill has already been selected. There is no `{query, expected_skill}` labeled test set anywhere in the repo, and nothing computes "did `registry.find()` pick the right skill." That's the one real gap, and it's cheap to fill (a CSV/YAML file + a script calling `find_with_scores()` in a loop) — it does not require building a new statistical or rollout framework, only a labeled dataset and a thin accuracy-computation wrapper around infrastructure that already exists.

### Concrete experiment design — §3.1 (deterministic post-processing) against a real skill

**Target**: `csat-action-advisor`'s EVALS.md criterion E4 ("business_rationale includes a quantified impact estimate," currently LLM-judged) — chosen because it recurs in near-identical form across `nps-action-advisor` and `ces-action-advisor` too, so the same experiment generalizes across 3 skills for one design.

- **Candidate deterministic check**: a regex/parser, e.g. `r"\d+(\.\d+)?\s*(%|pts?|points?|days?)"` over the `business_rationale` field (tunable against a few worked examples first).
- **Dataset**: CrystalOS is early-stage, so live production volume for this skill may be thin — don't wait for it. Pull whatever passing rows exist in `skill_examples` for the three skills (via the existing `list_skill_examples` admin query in `cdx.py`), and top up with ~40-60 synthetic `business_rationale` strings spanning the edge cases that actually matter: explicit `%`/`pts` figures, spelled-out numbers ("five percentage points"), ranges ("15-20%"), vague qualitative language with no number ("significantly," "meaningfully"), and numbers that aren't impact estimates (a survey ID, a sample size). Hand-label ground truth pass/fail for each.
- **Metric — do not just compare marginal pass rates.** The decision-relevant number is **agreement with human label** (a 2x2 confusion matrix: regex-vs-human, current-LLM-judge-vs-human), not "do the two methods have similar overall pass rates." Two methods can match on the aggregate pass rate while disagreeing on *which* items pass — that would look like a null result under `_check_significance()`'s two-proportion framing while actually hiding a real problem. **Reusing `_check_significance()` naively here would answer the wrong question** — it's built for "is variant B's marginal pass rate higher than baseline's," not "do two graders agree on the same items." Use raw agreement % and, ideally, Cohen's kappa (kappa is meaningfully more informative than plain agreement when the base rate is skewed — case in point: if 80% of business rationales already contain a number, a checker that always says "pass" gets 80% raw agreement for free).
- **Sample-size caveat**: 40-60 hand-labeled cases gives roughly a ±15 percentage-point margin on a binary agreement estimate at 95% confidence — enough to sanity-check "the regex agrees with a human ~90%+ of the time on the cases we thought of," not enough to certify it for a **must-pass** gate (E1/E2 in these same skills are already fully deterministic and must-pass — the right design there). Recommendation: pilot the swap only on E4 (a `>=0.75` weighted criterion, not must-pass), where a wrong verdict once in a while degrades a score, not silently ships bad output.
- **Secondary, free measurement**: cost/latency delta. One fewer LLM round-trip per skill invocation (the eval-judge call currently uses `get_model("insight_evaluate")` with `max_tokens=5`, so the token cost is trivial, but the round-trip latency and API-failure-mode exposure are not — a regex is ~0ms and cannot 500). Worth logging even if the agreement result is inconclusive, since it's a real, measurable, non-speculative win either way.
- **What this experiment would NOT settle**: whether the AIP paper's 53%→67% magnitude applies to CrystalOS. It settles the narrower, actually-answerable question — "is this one criterion safe to make deterministic" — which is the right scope for a first test, not a referendum on the whole pattern's expected lift.

## 5. Near-zero-risk vs. requires-a-bet

**Cheap to test, fully reversible, no architecture decision required:**
Provenance stamping; tool-error-contract naming/`assert_ok()` helper; verbose-output-to-log discipline; the removal-tracking table; the E4-style deterministic-criterion swap above; a description-field negative-phrasing experiment on 2-3 skill pairs that are plausible routing confusables (e.g. `csat-action-advisor` vs `nps-action-advisor` — both already carry "Distinguished from X" prose in their `description` field today, so this is refining an existing practice, not introducing a new one) measured against a small hand-built `{query, expected_skill}` set using `find_with_scores()` — all of these can be tried, measured, and reverted with no irreversible commitment.

**Correction worth flagging loudly**: the synthesis's literal Tier-1 #5 instruction ("add negative examples to `EXAMPLES.md`") is *not* one of these — as established in §2/§3, `EXAMPLES.md` has no runtime path into routing at all. The actually-cheap, actually-correct version of this recommendation is: add negative/counter-phrasing to the `description` frontmatter field (the only text `warm_router()` ever embeds), test it with the routing-accuracy harness above, not the markdown file the synthesis doc names.

**Require a real architectural bet before anything is measurable:**
The named hook-point/middleware refactor of `SkillRuntime.execute()` (Tier 2 #10) — there is no way to "partially" build named hook points; you build them, then you can measure whether future additions land in less code, which is an engineering-ergonomics question, not a quality-metric question, and none of the source research offers evidence that the *refactor itself* (as opposed to whatever it enables) moved any quality number anywhere. Similarly, AIP-style typed skill-graphs (Tier 3 #12) and the offline eval-case/grader harness (Tier 2 #9) are real builds — though the eval-harness build is meaningfully cheaper than it looks, since `cdx_test_skill` and `_check_significance` already provide two of its three necessary pieces (a routing/execution probe and a significance test); only the labeled-dataset-plus-YAML-case format layer is actually new work.

## 7. Recommendation

**Adopt selected patterns only.** The evidence base splits cleanly into three groups, and treating them uniformly would be the actual rigor failure here: (a) pure engineering-hygiene items (provenance stamping, tool-error contracts, log-routing, the removal-tracking table) that don't need benchmark evidence and can be adopted directly on code-review merit; (b) exactly one pattern — deterministic post-processing over LLM re-derivation — with genuine cross-source, non-vendor-selling-the-idea corroboration, already independently practiced in CrystalOS (`_build_viz_for_citations`), and cheaply extensible to at least 3 more skills via the E4 experiment in §4; and (c) a majority of the remaining headline claims (the OpenAI 73→85 number, the ≤12-skill ceiling, the various vendor-blog percentage swings) that are self-reported, measured on different models/mechanisms/task domains than CrystalOS's own, and should not be adopted on the strength of their cited numbers alone — CrystalOS already owns the statistical and rollout infrastructure (`resolve_variant`, `_check_significance`, `cdx_test_skill`) to cheaply test the ones worth testing (routing-relevant claims via a small labeled query set) before spending engineering effort on anything structural. A full rearchitecture or even a blanket "adopt incrementally" posture would be premature given how thin the evidence is for most of the individual claims; the right-sized move is to bank the hygiene wins now, run the one well-evidenced pattern's cheap experiment on a live skill, and gate any bigger structural bet (the hook-point refactor, typed skill-graphs) on a concrete enabling need rather than a borrowed performance number.
